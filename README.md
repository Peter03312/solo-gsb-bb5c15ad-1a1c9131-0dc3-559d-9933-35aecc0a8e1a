# 安全作业规程历史回溯服务（SOP History Service）

基于 **Python 3.12 + FastAPI + SQLite** 的双时间维（bitemporal）规程版本库，
提供可调用的 HTTP API：

- **首次发布**：录入规程编号、正文及 UTC 适用区间 `[起, 止)`，可携带
  前置规程编号列表（省略视为空）；
- **更正提交**：编号 + 被替代版本 + 该版本当前生效区间内的子区间 + 新正文，
  发布时间由服务端记录、不可回填；可携带前置规程编号列表
  （省略继承被替代版本，显式空列表清空）；
- **更正批量预演（只读）**：正式提交前按单条/批量同一套字段预演整批结果并
  指定非空作业区间；同批按输入顺序应用、后项可引用前项拟生成版本；全部合法
  返回各项拟生成版本号、最终前置清单及指定区间内提交前后实际适用版本不同的
  最大片段，任一非法指出位置与现有原因、不返回部分成功；预演不写版本、不占
  版本号、不改变历史，预演结果不保证可提交；
- **值班审计变动日志（增量拉取）**：按**提交顺序**取回全站首次发布、更正与
  撤回事件；游标分页，同一新提交批次按请求顺序排列且不可跨页拆开，游标只随
  已提交事务前进；并发写入或翻页期间的新提交不造成重现或遗漏，空页游标不变；
  升级前已有版本与撤回记录启动时一次性回填为单事件、不改写原记录，从起始
  游标即可完整读取。游标非法或每页上限装不下下一完整批次时明确报错。
- **回溯查询**：输入**作业时刻**与**知悉时刻**，返回截至知悉时刻已发布、
  且在作业时刻有效的正文与版本；无匹配返回空列表。
- **两知悉时刻对比**：输入规程编号、先后两个带时区的知悉时刻与非空作业区间，
  逐段比较同一规程在两侧知悉时刻下对该作业区间的实际适用内容，返回发生
  变化的最大片段（起止 + 两侧版本号/正文，无适用版本一侧为 `null`）。
- **更正撤回**：值班员发现更正误发布时，提交规程编号与更正版本号撤回；
  撤回时刻由服务端记录、不接受回填。撤回只追加事件、不删除原版本，
  撤回后该更正的适用子区间恢复父版本正文，父版本可在恢复区间再次更正。
- **作业规程包（固定 / 取回 / 复核）**：班组开工前按**作业时刻、知悉时刻及
  一组规程编号**固定作业规程包，返回包标识、各规程当时适用的版本与正文及
  两种时刻；编号重复、缺失或任一规程当时无适用正文时整体拒绝、不留包，
  知悉时刻不得晚于服务端当前时刻。包一经形成即不可变（后来的更正/撤回不
  影响按标识取回）；复核时以不早于包内知悉时刻、不晚于当前时刻的复核知悉
  时刻，按原作业时刻逐项返回包内版本、彼时有效版本及是否变化，并给整体
  是否仍一致。
- **前置规程清单（递归解析）**：班组按一份规程准备作业时，输入根编号、
  作业时刻与知悉时刻，在同一读取快照内按现有回溯语义递归展开各版本携带
  的前置编号，返回去重后的根及前置规程清单（前置优先，含编号、版本、
  正文）；根或引用编号不存在、任一规程当时无适用正文即说明缺口并整体
  失败，引用成环返回环路径、不返回部分清单。
- **跨时段前置规程清单（逐片段可用性）**：班组计划**跨时段**作业时，输入
  根编号、非空半开作业区间与带时区的知悉时刻，在同一读取快照内找出根及
  递归引用在全区间的版本切换边界，切成覆盖全区间、互不重叠的片段；每片段
  返回前置优先的去重清单及版本，根/引用缺失、无适用正文、引用成环时**保留
  该片段**并标明缺口链或环路径（整体结论为不可用）；相邻片段仅在清单与错误
  状态完全相同时合并，区间外的变动不影响结果。

更正只新增行、不改写任何旧行（append-only）；撤回同样只向 `withdrawals`
表追加一行事件、从不删除或改写版本行，因此"撤回前知悉时刻的查询结果"天然保持原样。

## 一、快速开始（一条命令）

前置：已安装 Docker 与 Docker Compose v2（`docker compose version` 可用）。

```bash
docker compose up --build
```

该命令依次完成：**安装依赖 → 初始化数据库（幂等建表）→ 启动 HTTP 服务**。
数据库文件位于命名卷 `sop-data` 内（容器路径 `/data/sop.db`），容器重建后数据保留。

服务启动后：

| 用途 | 地址 |
| --- | --- |
| API 根（端点列表） | <http://localhost:8080/> |
| 健康检查 | <http://localhost:8080/health> |
| Swagger 交互文档 | <http://localhost:8080/docs> |
| OpenAPI 描述 | <http://localhost:8080/openapi.json> |

后台运行 / 停止 / 清理：

```bash
docker compose up --build -d      # 后台
docker compose logs -f            # 查看日志
docker compose down               # 停止并移除容器（保留数据卷）
docker compose down -v            # 连同数据卷一起删除（清空历史）
```

### 不用 Docker 的本地运行方式

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
SOP_DB_PATH=./sop.db uvicorn app.main:app --host 0.0.0.0 --port 8080
# 数据库表在服务启动时自动创建，无需额外初始化步骤
```

## 二、配置项（环境变量）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SOP_DB_PATH` | `/data/sop.db` | SQLite 数据库文件路径，启动时自动建表 |
| `SOP_HOST` | `0.0.0.0` | HTTP 监听地址 |
| `SOP_PORT` | `8080` | **容器内**监听端口 |
| `SOP_BUSY_TIMEOUT_MS` | `5000` | SQLite 写锁等待毫秒数 |

修改宿主机映射端口（例如改用 18080）：

```bash
SOP_PORT=18080 docker compose up --build
# 此时访问 http://localhost:18080
```

> 说明：`docker-compose.yml` 中端口映射写作 `"${SOP_PORT:-8080}:8080"`，
> 即该变量改变的是宿主机侧端口；容器内始终监听 8080。

## 三、API 说明

所有时间均为 **ISO-8601 且必须带时区**（如 `2026-03-01T00:00:00Z` 或
`2026-03-01T08:00:00+08:00`），服务端统一规范化为 UTC 微秒串：
`YYYY-MM-DDTHH:MM:SS.ffffffZ`。区间一律为**左闭右开 `[起, 止)`**。

### 1. 首次发布 `POST /api/v1/releases`

请求体支持单条对象，或 `{"items": [...]}` 批量提交（整批原子，任一非法全部不入库）。

```json
{
  "number": "SOP-001",
  "body": "初版正文：进入车间必须佩戴护目镜。",
  "valid_start": "2026-01-01T00:00:00Z",
  "valid_end":   "2027-01-01T00:00:00Z",
  "prerequisites": ["SOP-010", "SOP-020"]
}
```

- 成功 `201`，返回服务端记录的 `published_at` 与版本号（首版 `revision=0`），
  并回显落库后的 `prerequisites`。
- `prerequisites` 为**可选**的前置规程编号列表：省略视为空列表；列表不得
  含空白编号（`422 invalid_number`）或重复编号（`422
  duplicate_prerequisite_number`）；**写入时不校验编号是否存在**——前置
  规程可以晚于引用者发布，存在性在递归解析（第 8 节）时按当时数据判定。
- 编号已存在 → `409 duplicate_number`。
- `起 >= 止`、缺时区等 → `422 invalid_interval / invalid_time`。
- 请求中出现 `published_at` 等额外字段 → `422 validation_error`（禁止回填）。

### 2. 提交更正 `POST /api/v1/corrections`

```json
{
  "number": "SOP-001",
  "base_revision": 0,
  "valid_start": "2026-03-01T00:00:00Z",
  "valid_end":   "2026-04-01T00:00:00Z",
  "body": "更正正文：3 月检修期还须穿戴防割手套。"
}
```

语义与校验（任一不满足则**整体拒绝、不写任何历史**）：

1. 子区间必须整体落在被替代版本的适用区间内，否则 `422 invalid_interval`；
2. 子区间必须落在被替代版本的**当前仍生效区间**（自身区间减去其已发布子更正）
   内；落在已被覆盖处 → `409 expired_base_version`（过期基版，响应中带
   `remaining_intervals` 提示当前可更正区间；应改以最新正文版本为基版）；
3. 同一批次中对同一被替代版本的多条更正子区间不得相互重叠，
   否则 `409 concurrent_correction_conflict`，整批回滚；
4. 编号不存在 → `404 not_found`；基版版本号不存在 → `404 base_version_not_found`。

更正版本号 `revision` 在该规程内递增；`supersedes_revision` 标明被替代版本，
支持"更正之更正"的版本链。同批条目按顺序处理，可在同一批中先更正 r0 得到 r1、
再以 r1 为基版继续更正。

更正同样可携带可选的 `prerequisites`：**省略则继承被替代版本**的前置编号
列表（基版行不可变，写入时复制即等价继承），**显式空列表 `[]` 表示清空**，
显式非空列表整体替换；校验规则与首次发布一致（无空白、无重复、不校验
存在性）。响应回显该版本落库后的实际列表。

### 3. 撤回更正 `POST /api/v1/withdrawals`

值班员发现**更正误发布**时使用。请求体只含规程编号与更正版本号，同样支持
单条对象或 `{"items": [...]}` 批量（整批原子，任一非法全部不追加事件）：

```json
{
  "number": "SOP-001",
  "revision": 1
}
```

- 撤回时刻 `withdrawn_at` 与发布时刻一样**由服务端单调时钟记录，接口不接受
  该字段**（请求中出现 `withdrawn_at` 等额外字段 → `422 validation_error`）。
- **撤回只追加事件**：向 `withdrawals` 表插入一行，绝不删除或改写 versions 行。
- 成功 `201`，返回服务端记录的 `withdrawn_at` 与被撤回版本信息（编号、版本号、
  父版本号、正文、适用区间、原 `published_at`、`withdrawn_at`）。

可撤回条件（任一不满足则**整体拒绝、不追加任何事件、不改变历史**）：

| 情况 | 状态码 | error.code |
| --- | --- | --- |
| 规程编号不存在 | `404` | `not_found` |
| 版本号在该规程下不存在 | `404` | `revision_not_found` |
| 撤回的是**首版** r0（首版只能更正、不能撤回） | `409` | `first_revision_not_withdrawable` |
| 该更正**已经撤回**（撤回事件只追加一次） | `409` | `already_withdrawn`（响应带原 `withdrawn_at`） |
| 该版本**已有子更正**（撤回不删行，子更正即使自身已撤回也仍在历史中；可撤回的是当前仍生效的叶子更正） | `409` | `version_has_children`（响应带 `child_revisions`） |

撤回的双时间维效果：

- **撤回前的知悉时刻**：回溯与区间对比仍按原版本链还原，被撤回版本照常可见
  （可见条件 `published_at <= k` 且未撤回或 `withdrawn_at >= k`，
  两侧边界均含等号，与发布时刻约定对称）；
- **撤回后的知悉时刻**：被撤回更正不再可见，其适用子区间**恢复父版本正文**；
  父版本的可更正剩余区间重新包含该子区间，可直接以父版本为基版**再次更正**
  （以已撤回版本为基版提交更正 → `409 base_version_withdrawn`）；
- **历史接口**始终能看到被撤回版本及其 `withdrawn_at`（见第 4 节）。

撤回与并发更正共用同一把全局写锁，并在同一条 `BEGIN IMMEDIATE` 事务内完成
"资格校验 + 追加事件"，因此二者按确定的全局先后次序生效：对同一版本的并发
撤回只有一份成功（其余得到 `409 already_withdrawn`），任何知悉时刻下同一
作业区间至多存在一份当前正文。

### 4. 回溯查询 `GET /api/v1/effective`

| 查询参数 | 必填 | 说明 |
| --- | --- | --- |
| `work_time` | 是 | 作业时刻（ISO-8601 带时区） |
| `known_as_of` | 否 | 知悉时刻；缺省取服务端当前时刻 |

```bash
curl 'http://localhost:8080/api/v1/effective?work_time=2026-03-15T08:00:00Z&known_as_of=2026-05-01T00:00:00Z'
```

返回（按规程编号排序）：

```json
{
  "work_time": "2026-03-15T08:00:00.000000Z",
  "known_as_of": "2026-05-01T00:00:00.000000Z",
  "count": 1,
  "items": [
    {
      "number": "SOP-001",
      "revision": 1,
      "body": "更正正文：……",
      "valid_start": "2026-03-01T00:00:00.000000Z",
      "valid_end":   "2026-04-01T00:00:00.000000Z",
      "supersedes_revision": 0,
      "published_at": "2026-02-10T03:12:44.918203Z"
    }
  ]
}
```

- 只返回满足 `published_at <= known_as_of`、且 `valid_start <= work_time < valid_end`
  的版本；已撤回版本还须满足撤回时刻不早于知悉时刻（`withdrawn_at >= known_as_of`），
  撤回之后的查询会跳过它并回落到父版本。同一规程存在版本链时返回最深（最新）的
  有效版本；
- 更正仅覆盖指定子区间，其余作业时刻仍返回父版本正文；撤回更正后其子区间恢复
  父版本正文，但以撤回前的知悉时刻查询仍看到被撤回版本（历史不变）；
- 无任何匹配时返回 `200` 与 `{"count": 0, "items": []}`。

### 5. 版本历史（审计视图）`GET /api/v1/procedures/{number}/history`

返回该规程的全部版本，不做知悉时刻裁剪，供审计/排障使用。编号不存在 → `404`。
每个版本均带 `withdrawn_at` 字段：未撤回为 `null`，已撤回事发时为服务端记录的
撤回时刻（版本行本身始终保留）；并带 `prerequisites` 字段，即该版本各自携带
的前置规程编号列表（随版本留档，不改写历史）。

### 6. 两知悉时刻对比 `GET /api/v1/procedures/{number}/diff`

值班人员核对"同一段作业、先后两次知悉时看到的规程是否一致"。查询参数全部必填、
均为 ISO-8601 **带时区**时间：

| 参数 | 说明 |
| --- | --- |
| `known_before` | 较早的知悉时刻（严格早于 `known_after`） |
| `known_after` | 较晚的知悉时刻 |
| `work_start` | 作业区间起点（含） |
| `work_end` | 作业区间终点（不含） |

```bash
curl -sS --get 'http://localhost:8080/api/v1/procedures/SOP-001/diff' \
  --data-urlencode 'known_before=2026-02-01T00:00:00Z' \
  --data-urlencode 'known_after=2026-06-01T00:00:00Z' \
  --data-urlencode 'work_start=2026-01-01T00:00:00Z' \
  --data-urlencode 'work_end=2027-01-01T00:00:00Z'
```

语义：

- 各侧状态沿**现有更正链按发布时间**还原：仅纳入该知悉时刻下"仍生效"的版本
  （`published_at <= 知悉时刻` 且未撤回或撤回时刻不早于该知悉时刻），
  作业时刻落在哪些版本区间内就沿 `supersedes` 链取最深（最新）者；
  无任何可见版本覆盖时该侧记为 `null`；撤回只影响撤回之后的知悉时刻，
  撤回前一侧仍能看到被撤回版本（历史不变）；
- 用两侧可见版本的全部区间端点对作业区间 `[work_start, work_end)` 做左闭右开
  切分，片段内两侧版本各自恒定；再**合并首尾相接且两侧版本相同的相邻片段**；
- 只返回两侧版本不同的**最大片段**：逐段给出 `start/end` 与
  `before/after`（各自 `{"revision", "body"}` 或 `null`）；两侧版本相同
  （含两侧均无版本）的片段不返回；
- **是否变化只看版本号**：即使新版本正文与旧版完全相同，只要版本不同就算变化。

响应（沿用上面"3 月更正"的数据；前侧知悉时刻早于一切发布）：

```json
{
  "number": "SOP-001",
  "known_before": "2025-01-01T00:00:00.000000Z",
  "known_after": "2026-06-01T00:00:00.000000Z",
  "work_start": "2026-01-01T00:00:00.000000Z",
  "work_end": "2027-01-01T00:00:00.000000Z",
  "count": 3,
  "segments": [
    {"start": "2026-01-01T00:00:00.000000Z", "end": "2026-03-01T00:00:00.000000Z",
     "before": null, "after": {"revision": 0, "body": "初版正文：……"}},
    {"start": "2026-03-01T00:00:00.000000Z", "end": "2026-04-01T00:00:00.000000Z",
     "before": null, "after": {"revision": 1, "body": "更正正文：……"}},
    {"start": "2026-04-01T00:00:00.000000Z", "end": "2027-01-01T00:00:00.000000Z",
     "before": null, "after": {"revision": 0, "body": "初版正文：……"}}
  ]
}
```

无变化时 `200` 且 `{"count": 0, "segments": []}`。错误均为只读、不写任何历史：

| 情况 | 状态码 | error.code |
| --- | --- | --- |
| 规程编号不存在（或为空） | `404` | `not_found` |
| 任一时刻缺时区 / 不可解析 | `422` | `invalid_time` |
| `work_start >= work_end`（空作业区间） | `422` | `invalid_interval` |
| `known_before >= known_after`（知悉顺序颠倒或相等） | `422` | `invalid_known_order` |
| 缺少必填查询参数 | `422` | `validation_error` |

### 7. 作业规程包：固定 / 取回 / 复核

班组开工前把"这次作业涉及哪些规程、按什么时刻认定"一次性固定下来，之后
即使规程被更正或撤回，也能随时取回**固定时的原样内容**，并复核当前看到的
版本是否仍与包内一致。可见性、左闭右开区间、撤回边界全部沿用前述约定。

#### 7.1 固定作业规程包 `POST /api/v1/packages`

```json
{
  "work_time": "2026-03-15T08:00:00Z",
  "known_as_of": "2026-09-30T00:00:00Z",
  "numbers": ["SOP-001", "SOP-002"]
}
```

- `numbers` 非空、不得重复；服务端**保留调用方传入的编号顺序**。
- 固定在**单条 `BEGIN IMMEDIATE` 事务**内完成：事务的一致快照上解析每个
  规程在 `(work_time, known_as_of)` 下适用的版本并整包落库，校验失败即
  回滚——不会拼接并发写入前后的结果，也绝不留下半截包。
- 成功 `201`，返回：

```json
{
  "id": "8c5f0c4f9e1a4b0e9d7a2f6c1b8e3a4d",
  "work_time": "2026-03-15T08:00:00.000000Z",
  "known_as_of": "2026-09-30T00:00:00.000000Z",
  "created_at": "2026-10-05T07:12:31.441902Z",
  "count": 2,
  "items": [
    {"number": "SOP-001", "revision": 1, "body": "……",
     "valid_start": "2026-03-01T00:00:00.000000Z",
     "valid_end":   "2026-04-01T00:00:00.000000Z",
     "supersedes_revision": 0,
     "published_at": "2026-02-10T03:12:44.918203Z"},
    {"number": "SOP-002", "revision": 0, "body": "……", "...": "..."}
  ]
}
```

拒绝情况（任一命中即**整体拒绝、不留包**）：

| 情况 | 状态码 | error.code |
| --- | --- | --- |
| 编号在列表中重复 | `422` | `duplicate_package_number`（details 带 `index`/`number`） |
| 某编号不存在 | `404` | `procedure_not_found`（details 带 `index`/`number`） |
| 某规程在该作业时刻、该知悉时刻下无已发布且生效的适用正文 | `409` | `no_applicable_version` |
| `known_as_of` 晚于服务端当前时刻 | `422` | `known_as_of_in_future` |
| 时刻缺时区/不可解析、编号为空串 | `422` | `invalid_time` / `invalid_number` |
| `numbers` 为空/缺失、出现 `created_at` 等额外字段 | `422` | `validation_error` |

> "无适用正文"覆盖两种数据情形：该知悉时刻下尚无已发布版本，或作业时刻
> 不在任何可见版本的 `[valid_start, valid_end)` 内（含已被撤回且回落不到
> 其他版本时）。固定时刻 `created_at` 由服务端单调时钟记录，接口不接受回填。

#### 7.2 按标识取回 `GET /api/v1/packages/{id}`

返回与固定成功时**完全相同**的响应。包内容（版本号、正文、区间、发布时刻）
在固定时整包复制为快照写入 `package_items`，此后的更正、撤回只作用于
`versions`/`withdrawals`，因此取回结果永远保持原样。标识不存在 →
`404 package_not_found`。

#### 7.3 复核 `GET /api/v1/packages/{id}/review?known_as_of=...`

`known_as_of`（复核知悉时刻）必须**不早于包内知悉时刻**、且**不晚于服务端
当前时刻**；服务端按**包内原作业时刻**、以同一数据快照逐项重新解析彼时有效
版本：

```bash
curl -sS 'http://localhost:8080/api/v1/packages/8c5f0c4f9e1a4b0e9d7a2f6c1b8e3a4d/review?known_as_of=2026-10-05T00:00:00Z'
```

```json

  "package_known_as_of": "2026-09-30T00:00:00.000000Z",
  "known_as_of": "2026-10-05T00:00:00.000000Z",

  "items": [
    {"number": "SOP-001",
     "pinned":  {"revision": 1, "body": "包内版本全文……",
                 "valid_start": "……", "valid_end": "……",
                 "supersedes_revision": 0, "published_at": "……"},
     "current": {"revision": 2, "body": "彼时有效版本全文……",
                 "valid_start": "……", "valid_end": "……",
```

- `pinned` 为包内固定版本（快照），`current` 为复核知悉时刻下按原作业时刻

| 时刻缺时区/不可解析 | `422` | `invalid_time` |
| 缺少 `known_as_of` 参数 | `422` | `validation_error` |

### 8. 前置规程清单（递归解析）`GET /api/v1/procedures/{number}/closure`

班组按一份规程准备作业时，需连同该时点有效的**前置规程**一起核对。每个
版本可携带一份前置规程编号列表（见第 1、2 节）；本接口从根规程在
`(作业时刻, 知悉时刻)` 下的适用版本出发，沿该版本携带的前置编号递归
展开，返回去重后的根及前置规程清单。

| 查询参数 | 必填 | 说明 |
| --- | --- | --- |
| `work_time` | 是 | 作业时刻（ISO-8601 带时区） |
| `known_as_of` | 否 | 知悉时刻；缺省取服务端当前时刻（与第 4 节一致） |

```bash
curl -sS 'http://localhost:8080/api/v1/procedures/SOP-001/closure?work_time=2026-03-15T08:00:00Z&known_as_of=2026-05-01T00:00:00Z'
```

语义：

- 每个规程取 `(work_time, known_as_of)` 下的适用版本（可见性、左闭右开
  区间、撤回边界与第 4 节完全一致），展开的是**该版本**所携带的前置
  列表——引用随版本的适用区间、发布时间与撤回而变化，历史不改写；
- 全部解析在**同一只读快照**内完成，不会拼入并发写入的中间结果；
- 清单**前置优先**：任一规程排在其前置之后，根规程在最后；同一编号被
  多处引用只出现一次（去重）；清单项含编号、版本、正文（及区间、父
  版本号、发布时刻与各自的前置列表）。

响应示例（SOP-001 的适用版本携带前置 SOP-010，SOP-010 又携带 SOP-020）：

```json
{
  "root": "SOP-001",
  "work_time": "2026-03-15T08:00:00.000000Z",
  "known_as_of": "2026-05-01T00:00:00.000000Z",
  "count": 3,
  "items": [
    {"number": "SOP-020", "revision": 0, "body": "……", "prerequisites": [], "...": "..."},
    {"number": "SOP-010", "revision": 0, "body": "……", "prerequisites": ["SOP-020"], "...": "..."},
    {"number": "SOP-001", "revision": 1, "body": "……", "prerequisites": ["SOP-010"], "...": "..."}
  ]
}
```

缺口即**整体失败、不返回部分清单**（错误均为只读、不写历史）：

| 情况 | 状态码 | error.code |
| --- | --- | --- |
| 根规程编号不存在（或为空） | `404` | `not_found` |
| 引用链上的前置编号不存在 | `404` | `prerequisite_not_found`（details 带 `number` 与引用链 `path`） |
| 根或任一前置规程当时无适用正文 | `409` | `no_applicable_version`（details 带 `number`、`path` 与两种时刻） |
| 前置引用成环 | `409` | `prerequisite_cycle`（details.cycle 为环路径，如 `["A","B","A"]`） |
| 时刻缺时区/不可解析 | `422` | `invalid_time` |
| 缺少 `work_time` 参数 | `422` | `validation_error` |

### 9. 跨时段前置规程清单（逐片段可用性）`GET /api/v1/procedures/{number}/closure-plan`

班组计划**跨时段**作业（如一次检修从 2 月持续到 5 月）时，需要判断根规程
及其递归前置在**整个作业区间**内是否持续可用，并看清清单/版本在区间内的
切换点。本接口在语义上是第 8 节的"区间版"：单时刻解析、写入接口与启动方式
完全不变。

| 查询参数 | 必填 | 说明 |
| --- | --- | --- |
| `work_start` | 是 | 作业区间起点（含），ISO-8601 带时区 |
| `work_end` | 是 | 作业区间终点（不含）；必须严格晚于起点 |
| `known_as_of` | 否 | 知悉时刻；缺省取服务端当前时刻（与第 4、8 节一致） |

```bash
curl -sS --get 'http://localhost:8080/api/v1/procedures/SOP-001/closure-plan' \
  --data-urlencode 'work_start=2026-01-01T00:00:00Z' \
  --data-urlencode 'work_end=2027-01-01T00:00:00Z' \
  --data-urlencode 'known_as_of=2026-05-01T00:00:00Z'
```

语义：

- **同一只读快照**：结构性收集、切分与逐片段解析全部在一次读取快照内完成，
  不会拼入并发写入的中间结果；全程只读、**不写任何历史**。
- **边界收集**：沿"该知悉时刻下可见版本携带的前置编号"做传递展开，取根及
  递归可引用到的全部规程之**可见版本**（`published_at <= k` 且未撤回或
  `withdrawn_at >= k`）的适用区间端点，与作业区间求交后排序。引用随版本的
  适用区间、发布时间与撤回而变化，所有切换都只可能发生在这些端点上，因此
  **片段内部闭包恒定**；作业区间**之外**的版本端点被裁剪、不产生片段。
- **逐片段解析**：对每个左闭右开片段以其**起点**为代表作业时刻，按第 8 节
  完全相同的回溯与前置语义解析闭包——前置优先、按编号去重、根在最后，清单项
  含编号、版本、正文、区间、父版本号、发布时刻及各自的前置列表。片段
  `[起, 止)` 首尾相接，恰好覆盖整个作业区间、互不重叠。
- **缺口/成环保留片段**：与第 8 节"缺口即整体失败、不返回部分清单"不同，
  本接口**保留每一个片段**：根/引用编号不存在（`gaps[].code = not_found /
  prerequisite_not_found`）、某规程在片段内无适用正文（`no_applicable_version`）
  时，该片段照样返回并在 `gaps` 中给出**缺口链**（每项含 `code`、`number`、
  `path`，如 `["根","前置","缺失编号"]`），成环片段给出 `cycle` 环路径
  （如 `["A","B","A"]`）且保留成环前已完成的前置部分；这些片段
  `available=false`。顶层 `available` 仅在**全部**片段均可用时为 `true`。
- **合并规则**：仅合并**首尾相接**且"清单（含版本号/正文/区间/各自前置列表）
  与错误状态（缺口链列表/环路径）**完全相同**"的相邻片段；被中间状态隔开的
  两端相同片段、版本号不同的片段均不跨段合并。

### 10. 更正批量预演（只读、不落库）`POST /api/v1/corrections/preview`

值班员在**正式提交多条更正之前**，按"现有单条/批量更正的同一套字段与校验"
预演整批结果，并**指定一个非空作业区间**，用于核对这批更正将生成哪些版本、
最终前置清单是什么，以及指定区间内实际适用正文会怎样变化。预演**全程只读**：
不写版本、不占版本号、不推进发布时钟、不改变历史。

请求体与 `/api/v1/corrections` 完全一致（字段、单条对象 /
`{"items": [...]}` 批量两种形式均支持），另加两个必填的作业区间字段：

- **批量形式**：作业区间放在外层，与 `items` 同级；
- **单条对象形式**：作业区间随该条目一起给出。

```json
{
  "work_start": "2026-01-01T00:00:00Z",
  "work_end":   "2027-01-01T00:00:00Z",
  "items": [
    {"number": "SOP-001", "base_revision": 0,
     "valid_start": "2026-03-01T00:00:00Z", "valid_end": "2026-04-01T00:00:00Z",
     "body": "三月更正正文。"},
    {"number": "SOP-001", "base_revision": 1,
     "valid_start": "2026-03-10T00:00:00Z", "valid_end": "2026-03-20T00:00:00Z",
     "body": "对拟生成 r1 的再更正（后项引用同批前项）。"}
  ]
}
```

语义（与正式提交逐项对齐）：

- **按输入顺序应用同批前项**：在同一读取快照的内存副本上逐条应用，后项可
  引用前项**拟生成**的版本（如上例第 2 条以第 1 条拟生成的 `r1` 为被替代
  版本）；拟生成版本号 = 该规程当时最大版本号 +1（预演**不占用**该号）。
- **逐项沿用现有校验与省略继承规则**：子区间落在基版适用区间内
  （`invalid_interval`）、基版未撤回（`base_version_withdrawn`）、同批对同一
  基版的子区间互不重叠（`concurrent_correction_conflict`）、落在当前剩余生效
  区间（`expired_base_version`，带 `remaining_intervals`）、编号/基版存在
  （`not_found` / `base_version_not_found`）、正文非空、前置编号无空白/重复；
  前置编号**省略继承被替代版本、显式 `[]` 清空、显式非空整体替换**。
- **任一项非法即整体失败**：返回与正式提交**完全相同**的错误码/原因，
  `error.details.index` 指明出错条目（从 0 起），**不返回任何部分成功结果**。
- **全部合法（HTTP 200）** 时返回：
  - `items`：各项按输入顺序（带 `index`）的**拟生成版本号** `revision`、
    被替代版本 `supersedes_revision`、子区间、正文与**最终前置清单**
    `prerequisites`（省略时为继承结果；不含 `published_at`——预演不发布）；
  - `changes`：本批涉及的每个规程（按编号在输入中**首次出现**的顺序）在
    指定作业区间内，**提交前**（当前快照）与**提交后**（应用本批之后）实际
    适用版本不同的**最大片段**：`start/end` 与两侧 `before/after`
    （各为 `{"revision","body"}` 或 `null`），切分、合并与"是否变化只看
    版本号"的判定完全沿用第 6 节两知悉时刻对比；作业区间之外的变化不产生
    片段，区间端点做左闭右开裁剪；无变化时该规程 `count=0, segments=[]`。

```json
{
  "work_start": "2026-01-01T00:00:00.000000Z",
  "work_end":   "2027-01-01T00:00:00.000000Z",
  "known_as_of": "2026-10-05T07:12:31.441902Z",
  "count": 2,
  "items": [
    {"index": 0, "number": "SOP-001", "revision": 1, "supersedes_revision": 0,
     "valid_start": "2026-03-01T00:00:00.000000Z", "valid_end": "2026-04-01T00:00:00.000000Z",
     "body": "三月更正正文。", "prerequisites": ["SOP-010"]},
    {"index": 1, "number": "SOP-001", "revision": 2, "supersedes_revision": 1,
     "valid_start": "2026-03-10T00:00:00.000000Z", "valid_end": "2026-03-20T00:00:00.000000Z",
     "body": "对拟生成 r1 的再更正。", "prerequisites": ["SOP-010"]}
  ],
  "changes": [
    {"number": "SOP-001", "count": 3, "segments": [
      {"start": "2026-03-01T00:00:00.000000Z", "end": "2026-03-10T00:00:00.000000Z",
       "before": {"revision": 0, "body": "初版正文：……"},
       "after":  {"revision": 1, "body": "三月更正正文。"}},
      {"start": "2026-03-10T00:00:00.000000Z", "end": "2026-03-20T00:00:00.000000Z",
       "before": {"revision": 0, "body": "初版正文：……"},
       "after":  {"revision": 2, "body": "对拟生成 r1 的再更正。"}},
      {"start": "2026-03-20T00:00:00.000000Z", "end": "2026-04-01T00:00:00.000000Z",
       "before": {"revision": 0, "body": "初版正文：……"},
       "after":  {"revision": 1, "body": "三月更正正文。"}}
    ]}
  ]
}
```

> **预演结果不保证可提交**：预演只代表"该读取快照当时 + 应用这一批"的结果；
> 随后正式提交 `/api/v1/corrections` 仍须按**提交时的当时状态**重新校验
> （例如预演之后他人已占用同一区间，会得到 `expired_base_version` 等错误）。

| 情况 | 状态码 | error.code |
| --- | --- | --- |
| 某条目编号不存在 / 基版版本号不存在（`details.index` 指位置） | `404` | `not_found` / `base_version_not_found` |
| 条目子区间超出基版区间 / 作业区间空或倒置 | `422` | `invalid_interval` |
| 基版已撤回 / 已被既有更正覆盖 / 同批重叠 | `409` | `base_version_withdrawn` / `expired_base_version` / `concurrent_correction_conflict` |
| 正文为空、前置编号空白/重复、时刻缺时区 | `422` | `invalid_body` / `invalid_number` / `duplicate_prerequisite_number` / `invalid_time` |
| 缺少 `work_start`/`work_end`/`items`、出现 `published_at` 等额外字段 | `422` | `validation_error` |

### 11. 值班审计变动日志（增量拉取）`GET /api/v1/audit/events`

值班审计按**提交顺序**增量取回全站规程变动：首次发布、批量更正、撤回都
作为变动事件进入同一条只追加日志。支持游标分页，适合值班侧轮询/断点续传。

| 查询参数 | 必填 | 说明 |
| --- | --- | --- |
| `cursor` | 否 | 上一页响应返回的 `next_cursor`（不透明字符串）；省略、空或传 `0` 为**起始游标**，从升级前第一条历史事件开始 |
| `limit` | 否 | 每页**事件数**上限，整数 `1..1000`，默认 `100` |

```bash
curl -sS 'http://localhost:8080/api/v1/audit/events?cursor=0&limit=100'
```

响应：

```json
{
  "cursor": "0",
  "next_cursor": "3",
  "limit": 100,
  "has_more": true,
  "count": 2,
  "events": [
    {"operation": "release", "number": "SOP-001", "revision": 0,
     "event_time": "2026-02-10T03:12:44.918203Z",
     "batch_seq": 1, "position": 0},
    {"operation": "correction", "number": "SOP-001", "revision": 1,
     "event_time": "2026-03-02T09:00:00.104312Z",
     "batch_seq": 3, "position": 0}
  ]
}
```

语义（本轮契约）：

- **事件字段**：`operation`（`release` 首次发布 / `correction` 更正 /
  `withdrawal` 撤回）、`number` 规程编号、`revision` 版本号、`event_time`
  服务端时刻（发布/撤回时刻，UTC 微秒串）；另含 `batch_seq`/`position`
  供值班侧核对批次与页内顺序。
- **批次原子**：一次写请求（含批量首次发布 / 批量更正 / 批量撤回）= 一个
  **批次**（同 `batch_seq`），批次内事件严格按**请求顺序**排列且**分页不可
  拆开**。若游标后的下一整批事件数 `> limit`，返回 `422
  page_limit_too_small`（details 带 `batch_seq`/`batch_size`/`limit`），
  **不返回任何事件、游标不前进**；调大 `limit` 后以同一游标重试即可。
- **游标只随已提交事务前进**：审计批次与业务行在**同一条 `BEGIN IMMEDIATE`
  事务**内写入——写事务回滚（整批校验失败）时审计批次一并消失。整页在
  **进入时固定的只读快照**上读取，因此并发写入或翻页期间的新提交要么整批
  可见、要么整批不可见：反复翻页不会**重现**也不会**遗漏**。
- **空页保持游标不变**：没有新事件时 `count=0`、`events=[]`、
  `next_cursor == cursor`、`has_more=false`；值班侧持该游标稍后重试即可。
- **升级前历史**：服务启动时对升级前已存在的 `versions`/`withdrawals`
  执行**一次性、幂等的回填**——每条旧记录补成一个**单事件**批次（原始请求
  批次无法事后重建，故不合并），按服务端时刻与原始行顺序排列，从起始游标
  即可完整读取；回填**只向审计表追加，绝不改写任何原记录**（版本行、撤回
  行及其时间戳原样保留）。升级后新提交的事务继续追加在回填批次之后。
- **既有写入与查询契约、启动方式不变**：所有原有接口的请求/响应形状、
  错误码与 `docker compose up` 启动流程均保持可用。

轮询用法：首次省略 `cursor`（或传 `0`）；之后把每次响应的 `next_cursor`
作为下一次请求的 `cursor`，直到 `has_more=false`；随后持同一游标轮询，
空页原样返回该游标。游标不透明，**只能使用服务端返回的值**。

| 情况 | 状态码 | error.code |
| --- | --- | --- |
| 游标非数字、负数，或不指向任何已提交批次（如伪造/越界） | `422` | `invalid_cursor`（details 带回填值） |
| `limit` 非整数或不在 `1..1000` | `422` | `invalid_page_limit`（details 带 `max=1000`） |
| `limit` 装不下游标后的下一完整批次 | `422` | `page_limit_too_small`（details 带 `batch_seq`/`batch_size`） |

## 五、设计要点

- **双时间维**：每条版本行同时带适用区间（valid time）与发布时间
  （transaction time）。发布时间由服务端单调时钟生成，接口不接受该字段；
  所有写操作只 `INSERT`、从不 `UPDATE/DELETE` 业务行。
- **撤回即事件**：撤回不改写版本行，只在 `withdrawals` 表追加
  `(version_id, withdrawn_at)`（服务端时钟、`UNIQUE(version_id)`）。版本在
  知悉时刻 k 可见 ⇔ `published_at <= k` 且（未撤回或 `withdrawn_at >= k`）；
  撤回之后该区间恢复父版本正文，父版本剩余区间重新可更正。
- **版本树**：首版 `revision=0`；更正以 `supersedes_id` 指向被替代版本。
  父版本的"仍生效区间"= 自身区间 − 其全部**未撤回**子更正区间。查询时在
  候选版本中沿替代链取最深者。撤回仅允许作用于当前仍生效且没有任何子更正
  （子更正行即使自身已撤回也仍在历史中）的叶子更正；首版不可撤回。
- **作业规程包即快照**：`packages` 记录包的两种时刻与服务端固定时刻
  `created_at`；`package_items` 把每个规程当时适用版本的**正文连同版本号、
  区间、父版本号、发布时刻完整复制**（不做后期 JOIN），因此之后任何
  更正/撤回都只改活动历史、不触及包快照，按标识取回永远是固定时原样。
  固定在写事务的一致快照上"解析 + 落库"原子完成（失败回滚、不留包）；
  复核在显式只读快照事务（`BEGIN` 后事务内读到同一版本）内对所有规程逐项
  重新解析，保证 `all_match` 不拼接并发写入。是否变化只看版本号，撤回后
  回落父版本、无任何适用版本（`current=null`）均记为变化。
- **前置规程按版本留档**：`prerequisites(version_id, position, number)`
  与版本行同事务插入、只追加不改写。首次发布省略视为空；更正省略在写入
  时复制被替代版本的列表（基版行不可变，复制即等价继承），显式空列表
  清空。写入只校验"无空白、无重复"，不校验存在性（前置可晚发布）。
  引用是否生效完全由所属版本的双时间维可见性决定，因此随适用区间、
  发布时间与撤回自然变化，任何历史知悉时刻看到的都是当时的列表。
  递归解析在单只读快照内做迭代式后序遍历：前置优先、按编号去重、根在
  最后；缺口（根/引用不存在、当时无适用正文）带引用链整体失败，环检测
  基于当前解析栈、返回环路径，深链不触发递归上限。
- **跨时段闭包即逐片段状态**：`closure-plan` 在同一只读快照内先沿"可见
  版本携带的前置编号"结构性收集作业区间内可传递引用到的全部规程，取这些
  规程可见版本与作业区间相交的适用区间端点作为唯一切换边界（片段内各规程
  适用版本与其前置列表均恒定，区间外变动被裁剪），再以每个左闭右开片段的
  起点为代表作业时刻复用单时刻闭包解析。单时刻解析对缺口/环是"整体失败"，
  区间版则把解析器改为"首次缺口/环即停止展开、保留已完成的前置优先部分"，
  因此缺口（根 `not_found`、引用 `prerequisite_not_found`、无适用正文
  `no_applicable_version`，均带缺口链 `path`）与环（`cycle` 环路径）表现为
  **片段状态**而非请求错误；相邻片段仅在"清单 + 缺口链 + 环路径"完全相同
  时合并。全程只读，非法区间/时间直接 422、不写历史。
- **更正预演即"只读快照副本上的同一份提交逻辑"**：`corrections/preview`
  在一只读快照事务内把当时全部业务表（含 `sqlite_sequence`）完整复制进
  内存库，随后在副本上运行与正式提交**逐行相同**的 `_apply_corrections`
  （正式提交也调用该函数），因此预演天然逐项沿用剩余区间、同批重叠、正文
  与前置编号校验及"省略继承 / 显式清空"，同批按输入顺序生效、后项可引用
  前项拟生成版本，错误码/原因/位置与正式提交完全一致；副本在事务结束后
  丢弃，故预演不写版本、不占版本号、不推进服务端时钟、不改变历史。差异
  片段在同一快照（提交前）与副本（提交后）两侧，复用两知悉时刻对比的端点
  切分、相邻合并与"只看版本号"判定，按本批涉及规程首次出现顺序输出。
- **原子拒绝**：写操作在单条 `BEGIN IMMEDIATE` 写事务内完成"校验 + 插入"，
  进程内写锁串行化；校验失败即回滚，绝不留下半截历史。撤回与并发更正由此
  按确定次序先后生效，同一区间不会并存两份当前正文。
- **值班审计即提交事务批次**：`audit_batches`（每个已提交写事务一行，
  自增 `seq` 即游标位点）与 `audit_events`（批次内按请求顺序、带操作类型/
  规程编号/版本号/服务端时刻）在业务写事务**同一事务**内追加；写事务回滚
  则审计行一并消失。整页读取在进入时固定的只读快照上完成：并发或翻页期间
  的新提交整批可见或整批不可见，配合"游标 = 最近已完整交付批次 seq"，
  不重现、不遗漏。同一批次不可跨页：`limit` 装不下下一整批时返回
  `page_limit_too_small` 且游标不前进；空页游标原样返回。服务启动时对
  升级前 `versions`/`withdrawals` 做一次幂等回填，逐条生成单事件批次
  （按服务端时刻、发布先于撤回的次序），只追加审计表、不改写任何原记录。
- **时间存储**：统一存为定长 UTC 字符串，字典序与时间序一致，区间过滤直接用
  字符串比较；WAL 模式下读写不互斥。
